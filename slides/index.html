Les codes à usage unique

OTP, pour One-Time Password : 20 minutes.

Un mot de passe seul ne suffit plus

Les bases fuient, et on réutilise le même mot de passe d'un site à l'autre. Il faut une deuxième preuve, d'une autre nature.

Ce que je sais

Un mot de passe, un code PIN

Ce que je possède

Mon téléphone : c'est là qu'intervient l'OTP

Ce que je suis

Une empreinte, un visage

La double authentification combine deux de ces trois familles.

Pour les non-techs : « ce que je possède » se prouve en montrant quelque chose que seul mon téléphone peut produire. C'est le code.

Deux montres et un secret

Une seule fois, à l'inscription : le QR code dépose le même secret des deux côtés.

Téléphone

secret + heure qu'il est

=
Serveur

secret + heure qu'il est

Ensuite, ils ne se parlent plus. Même secret et même heure donnent le même code.

C'est LE message de la partie. Laisser les codes changer en direct devant la salle : ils basculent en même temps. Personne n'a rien envoyé.

L'heure, en tranches de 30 secondes

Secondes depuis le 1er janvier 1970
Divisé par 30, sans les décimales
Prochaine tranche dans

Ce numéro de tranche, identique partout dans le monde au même instant, est la partie « heure » du calcul.

Pointer le numéro de tranche surligné : il change toutes les 30 secondes, en même temps sur le téléphone et sur le serveur.

Côté dev : tout tient dans une formule

code = tronque(HMAC-SHA1(secret, tranche)) mod 106
  • TOTP (RFC 6238) : un HMAC-SHA1 du secret et du numéro de tranche de 30 secondes, ramené à 6 chiffres par une « troncature dynamique ».
  • Un HMAC, c'est une empreinte qu'on ne peut produire qu'en connaissant le secret. On le recroisera dans la partie 2.
Pour les devs. Les autres peuvent retenir : « une moulinette cryptographique standard ». Annoncer le HMAC comme fil rouge vers les JWT. Si on demande : TOTP réutilise le calcul de HOTP (RFC 4226), où le compteur est le nombre de codes déjà utilisés ; TOTP remplace ce compteur par l'heure.

Ce que contient vraiment le QR code

otpauth://totp/Apero:demo ?secret=APEROTECHAPEROTECHAPEROTECHAPERO &issuer=Apero

C'est tout ce qui est échangé, une seule fois. Le secret est encodé en base32.

Quelqu'un qui photographie ce QR code possède votre double authentification.

Ce secret est justement celui qui calcule le code de la première slide. Rappeler qu'il ne faut jamais partager un QR d'enrôlement en capture d'écran.

Tout l'algorithme, en Java

String totp(byte[] key, long counter) throws Exception {
    Mac mac = Mac.getInstance("HmacSHA1");
    mac.init(new SecretKeySpec(key, "HmacSHA1"));
    byte[] h = mac.doFinal(ByteBuffer.allocate(8).putLong(counter).array());

    int offset = h[h.length - 1] & 0x0F;                  // troncature dynamique
    int code = ByteBuffer.wrap(h, offset, 4).getInt() & 0x7FFFFFFF;
    return "%06d".formatted(code % 1_000_000);
}

totp(key, Instant.now().getEpochSecond() / 30);           // tranche de 30 s

Aucune dépendance : javax.crypto.Mac est dans le JDK. otp/Totp.java est un fichier Java 25 qui se lance avec java Totp.java, sans classe ni import.

Lire le code de haut en bas : HMAC, on prend 4 octets à une position donnée par le dernier octet, on garde 6 chiffres. Le format de fichier compact de Java 25 est un clin d'œil à un futur Apero Tech sur Java.

Démo : le téléphone en mode avion

  1. java Totp.java enroll | qrencode -t ansiutf8Génère un secret et affiche son QR code
  2. Un volontaire scanne le QR avec son appli d'authentification
  3. Il passe son téléphone en mode avion
  4. java Totp.javaLe terminal et le téléphone affichent le même code, au même instant
Faire scanner par un non-dev, qui lit son code à voix haute. Le mode avion est le moment qui marque. Si l'appli bloque la recopie d'écran ou si le scan échoue, coller le secret dans le champ de droite.

  • Sans jeton, la requête passe avec le rôle anon, qui ne peut que lire.
  • Les droits sont des GRANT SQL classiques ; pour filtrer ligne par ligne, la Row Level Security de Postgres.
  • Le lien avec la partie 1 : l'OTP vérifie qui vous êtes au login, le JWT transporte ensuite cette identité jusqu'à la base.
PostgREST se connecte avec un rôle authenticator qui ne peut rien faire seul : il ne fait qu'endosser anon ou membre.

Le contenu n'est pas chiffré, il est signé : tout le monde peut le lire, personne ne peut le modifier sans casser la signature. C'est le pont avec la partie 1.
